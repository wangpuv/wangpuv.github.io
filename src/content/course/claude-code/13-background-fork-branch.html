本课回答一个问题：想换个思路，或者让 Claude 在后台继续干活，应该用哪个命令？

适合：已经会进行连续对话，准备同时推进几件事的人。

📌 按 2026 年 9 月官方文档核对。本文主要介绍 Claude Code v2.1.212 及以后、agent view 开启时的行为；相关功能仍在研究预览阶段。旧版本和关闭 agent view 的情况，见文中版本提醒。

一、先问：谁去后台，你留在哪？

上一课，我们讨论了 /batch 如何组织大规模并行改动。这一课先不追求“同时干很多事”，而是弄清楚几个容易混淆的命令。

假设你已经和 Claude 讨论了一轮登录模块的设计。现在有三个不同的想法：

  • 想保留现有讨论，自己换个方案继续聊；
  • 想让另一份会话去调查问题，自己留在原来的对话；
  • 想让眼前这份会话继续工作，先把终端腾出来。

这分别对应 /branch、/fork 和 /background。

记住这个顺序就容易了：

/branch：你进入副本。

/fork：副本去后台，你留在原处。

/background：当前会话去后台，终端腾出来。

它们解决的是“对话怎么继续”，不是三个不同档位的加速按钮。

二、/branch：换一条思路，自己接着聊

在当前 Claude Code 对话中输入：

/branch login-plan-b

它会从当前位置复制一份对话，并把你切换到副本。原来的对话保留，可以通过 /resume 找回。

例如，你已经讨论了方案 A，现在想试试方案 B：

先不要修改文件。
基于已有需求，改用方案 B 分析登录流程。
比较它与方案 A 的实现复杂度、兼容风险和测试成本。

这样做的好处，是两条讨论路线可以分别展开。你不必先删除方案 A 的讨论，也不用从头重述需求。

但一定要注意：这里的 branch 是对话分支，不是 Git 分支，更不是一份自动隔离的代码目录。

如果你在副本中修改了文件，再恢复原对话，磁盘上的修改不会因为切回聊天记录就消失。

所以，比较方案时可以先限制为“只讨论、不改文件”。决定实际实现两套代码时，再安排独立的 worktree、明确各自的起点和验收方式。

三、/fork：复制一份去后台，自己留在原对话

如果不是自己换条路线，而是想让另一份会话去处理一件事，可以输入：

/fork 检查登录模块的测试覆盖，只阅读文件，不修改代码。列出缺失场景和对应文件位置。

在本文介绍的新版本行为中，副本会继承分叉前的对话，并作为独立后台会话执行这条指令；你仍然留在原对话里。

如果只输入 /fork 而不附带任务，副本会等待你的第一条指令，不会自动猜测接下来要做什么。

这里的“独立”很重要：**副本后来发生的对话，不会自动写回原对话。**它不是“叫一个助手，做完自动把结果交回来”的同义词。

如果我就是想让它做完回报呢？

当前版本对应的是 /subtask：

/subtask 检查登录模块的测试覆盖，只阅读文件，不修改代码。完成后返回缺失场景清单。

它启动继承当前对话的后台子代理，结果会返回当前会话。

可以这样选择：

  • 想单独跟进另一份完整对话：考虑 /fork。
  • 想委派一个旁支任务，拿回结果继续主线：考虑 /subtask。

旧教程为什么说得不一样？

在 v2.1.161–v2.1.211 中，/fork 的确是后台子代理用法。v2.1.212 起，这一用法改由 /subtask 承担。

另外，关闭 agent view 时，/fork 仍保留子代理行为，/subtask 不可用。

如果你的界面与本文不一致，先在系统终端运行 claude --version，再在 Claude Code 中查看 /help，确认版本和功能是否开启。不要只凭命令名称判断行为。

四、/background：让眼前这份会话继续工作

假设当前会话已经掌握任务上下文，你希望它接着分析，只是暂时不占用这个终端：

/background 继续整理当前调查结果，列出证据、待确认问题和下一步建议，不修改代码。

也可以使用简写 /bg。

与 /fork 不同，这次送到后台的是当前会话，而不是留着当前对话、再派一个副本出去。

后台也不是无人值守的保证。任务可能需要你回答问题、处理权限提示，或者补充缺失信息。

这里的后台会话进程运行在你的电脑上，并不是把执行环境迁移到云端；模型请求仍使用当前配置的服务，不代表模型推理也完全在本机进行。

关机后任务不会继续执行。机器休眠时会话可以保留，但不要把休眠时间按任务持续运行来规划。

我建议第一次尝试时，先用一项边界明确的只读调查：让它列清单、给证据，自己稍后回来检查。熟悉状态和接管方式后，再安排会修改代码的任务。

五、看进度：/tasks 和 claude agents 不是同一个入口

“后台任务”听起来像一个篮子，但实际需要区分两层。

当前会话里面的后台工作

在 Claude Code 对话中输入：

/tasks

它用于查看和管理当前会话内的后台工作，例如后台命令和子代理，也会显示已完成的子代理。/bashes 是它的别名。

独立的后台会话

在系统终端输入：

claude agents

这是 agent view 的入口，用来查看和接管独立后台会话，包括本文介绍的 /fork 副本与 /background 会话。

注意，它前面没有斜杠，也不是在 Claude 对话里输入 /agents。这两个写法不能互换。

进入列表后，可以这样查看和接管：

  1. 用方向键选中目标会话，按 Space 查看近期输出，也可以在查看面板中回复它。
  2. 想进入完整对话时，选中该会话后按 Enter。
  3. 在会话的空输入框中按 ←，脱离会话并返回列表；这不会停止后台会话。

**给已有会话追加指令，要在它的查看面板或完整对话中输入。**列表中的新任务输入框会创建另一份后台会话，不是给选中的会话追加消息。具体按键以当前界面提示为准。

查看时，我建议按这个顺序检查：

  1. 它是在工作，还是在等我输入？
  2. 是否出现权限、依赖或任务范围问题？
  3. 结果放在哪里，有哪些证据可供核验？
  4. 如果修改了代码，改动是否在预期的工作目录？

**退出查看界面、停止执行、删除会话，是三种不同动作。**不要为了返回终端而随手删除任务；尤其存在代码改动时，先确认成果已经保留。

六、最容易踩的坑：对话分开，不等于文件隔离

想象两个会话同时处理登录模块：一个改接口响应，另一个改测试。如果它们实际操作同一个目录，就可能互相影响。

命令执行成功，只能说明会话安排好了，不能代替工作目录检查。

当前文档说明，v2.1.221 起，/fork 在非原地编辑的情形下会指示副本先创建自己的 worktree 再改代码。但这有配置和环境上的例外，不能概括成“用了 /fork 就一定自动隔离”。

真正要并行改代码之前，先让每个会话报告：

开始修改前，请确认并报告：
1. 当前工作目录；
2. 当前 Git 分支与起始提交；
3. 这次允许修改的文件范围；
4. 验证方式。
如果目录或任务范围与其他会话冲突，先停下来说明，不要直接修改。

这是一条操作建议，不是权限沙箱。还需要核对实际目录和变更，不能只看一句“已确认”。

另外，多个任务同时运行会共同消耗使用额度，也会竞争本机资源。先用一个小任务跑通“派出、查看、接管、验收”，比一次开很多任务更容易发现问题。

七、课后练习：先做一轮只读分工

选一个你熟悉的小模块，按下面的顺序练习：

  1. 在主会话中说清模块目标，并明确“本轮不修改代码”。
  2. 用 /branch 开一条讨论路线，比较另一种设计。
  3. 用 /resume 回到原对话后，用 /fork 派出一项只读调查。
  4. 新开一个终端窗口或标签页，运行 claude agents，找到副本并按 Space 查看结果。原终端仍保留主会话。
  5. 切回原终端，在主会话中用 /subtask 做一项小调查，观察结果回到主会话的区别。
  6. 等这项子任务完成后，在主会话中输入 /background 整理本轮调查结论与待确认问题，不修改代码。然后运行 claude agents，找到它，按 Enter 进入完整对话；查看后，在空输入框按 ← 返回列表，完成一轮“后台运行—查看—接管—返回”。

不需要故意制造大任务。只要能说清楚“我在哪一份对话里、另一项工作在哪里、结果应该去哪里找”，这课的核心就掌握了。

本课小结

  • /branch：保留原对话，自己进入副本。
  • /fork：副本去后台，自己留在原对话；注意版本与 agent view 设置。
  • /background：当前会话去后台，释放终端。
  • /subtask：委派后台子代理，让结果回到当前会话。
  • /tasks / claude agents：分别查看会话内后台工作和独立后台会话。

最后记住一句话：先弄清对话在哪里，再确认代码改在哪里。
