本课回答一个问题：一项改动涉及很多文件，什么时候可以放心交给多个 Claude 同时做？

适合：已经会使用子代理，准备处理跨模块迁移、批量改造或重复性修改的人。

📌 命令行为按 Claude Code 官方文档核对至 2026 年 9 月。文中的任务判断与执行建议是工程实践分析；实际菜单和执行结果以当前版本与项目环境为准。

一、/batch 会做什么

在 Claude Code 的 Git 项目会话中，可以输入：

/batch <改动要求>

它是 Claude Code 自带的一个 Skill，用来组织跨代码库的并行改动。按当前官方说明，它会先研究代码库，把工作拆成 5–30 个独立单元，给出方案；得到批准后，再为各单元启动后台子代理。

每个子代理在独立的 Git worktree 中实现自己的部分、运行测试，并创建 Pull Request（PR，合并请求）。

这里需要分清三个角色：

  • Skill：把调查、拆分和执行步骤组织起来；
  • 子代理：承担各自的实现工作；
  • worktree：为每个单元提供独立的代码工作目录。

PR 是接下来审查和合并的入口。成功创建 PR，还需要相应的远程仓库访问、认证和权限；它不是只要本地有 Git 就一定能完成的步骤。

“5–30 个单元”描述的是当前工作流的拆分范围，不代表每个项目都应该同时运行 30 个任务。如果只有两三个小修改，直接在主会话完成，或明确委派少量子代理，往往更合适。

二、并行之前，先问三个问题

决定能不能用 /batch 的关键，是这些工作能否独立推进。

1. 规则明确了吗？

不同代理读到要求后，应该能做出一致的决定。

例如，“按已经确定的新日志接口替换各模块中的旧调用”，通常比“把日志系统设计得更好”明确得多。

不一定非得是简单查找替换，但接口约定、行为边界和例外处理要先说清楚。如果几个代理还得各自决定“到底应该怎么设计”，就容易得到互不兼容的实现。

2. 单元真的独立吗？

尽量按模块或清晰的文件归属拆分，避免多个单元同时修改公共配置、依赖锁文件或同一个核心接口。

但文件不重叠，也不代表行为没有依赖。

比如，一个代理修改响应字段，另一个代理修改读取这个字段的客户端。两边编辑的是不同文件，却必须遵守同一套接口约定，也可能需要一起发布。

可以共享已经确定的规则；需要避免的是执行过程中反复协商规则，或者一个单元必须等另一个单元完成才能验证。

3. 结果能够验收吗？

每个单元都应有清楚的完成标准：改哪些位置、保留什么行为、运行哪些检查、遇到哪些情况应报告而非自行决定。

同时还要有整体验收：各单元测试通过后，合并起来是否仍然满足接口和业务要求？

这三问是本课建议的判断方法，不是 /batch 内置的强制检查。任何一项没有准备好，都应该先缩小范围、补充设计或建立验证方式。

三、四类任务，怎样判断

情况 A：给路由补充 response_model

如果响应模型已经确定，路由之间比较独立，每个路由都有对应测试，可以考虑按模块并行补齐。

但不要把它当成纯粹的注释修改。以 FastAPI 为例，response_model 会参与响应数据的验证、转换与过滤。添加之后，实际返回字段和错误行为都可能变化。

所以前提是：先确认接口应该返回什么，并验证新增模型不会意外丢失字段或暴露不该返回的数据。

情况 B：把一个字段统一改名

如果只是内部局部变量，引用范围明确，通常容易分区处理。

如果是 API 字段、数据库列或跨服务消息字段，就不能仅凭“大家换成同一个名字”判断它独立。还需要确定：

  • 旧名称是否继续兼容；
  • 数据是否需要迁移；
  • 调用方何时升级；
  • 各 PR 是否可以独立合并和部署。

可以先完成公共兼容层，再让多个模块按同一规则迁移。先解除依赖，再扩大并行范围。

情况 C：引入多租户隔离

租户从哪里识别、如何传入数据访问层、哪些查询必须限制租户、后台任务怎样处理，这些都属于共享的设计决策。

在这些规则尚未确定时，直接让认证、数据库和路由三个代理各改各的，风险很高。

更适合先在主会话完成设计和一条端到端样例，再评估剩余模块能否按固定规则分批迁移。

情况 D：Pydantic v1 迁移到 v2

这是“部分适合并行”的典型例子。

一些调用形式有明确的迁移方向，例如 .dict() 到 .model_dump()、.parse_obj() 到 .model_validate()。但仍要检查参数和实际行为，不能只看方法名。

校验器和模型配置尤其需要提前分析：@validator 到 @field_validator 涉及参数、签名和验证行为差异；旧 Config 类迁移到 model_config 时，也可能遇到已移除或改名的配置项。

先确定目标版本、迁移规则和代表性测试，再把没有跨模型依赖的部分拆出去。嵌套模型、共享基类和公共验证逻辑，应单独处理或纳入同一个有明确责任边界的单元。

这里不展开具体迁移教程；本课要练的是：看见批量工作时，先找出其中需要共同决定的部分。

四、给 /batch 一份可以执行的要求

下面是一份提示词示例。假设你已经实现并验证了公共日志接口，接下来要迁移各业务模块的调用。

开始前，确认公共日志接口和迁移规则文件已提交，并包含在各单元使用的工作基线中，也就是创建 worktree 时采用的代码版本。不要依赖当前目录里的未提交修改；即使已经提交，也要确认所选基线包含这些提交。

/batch 将 src/modules/ 下的旧日志调用迁移到已经实现的新日志接口。

迁移规则以 docs/logging-migration.md 为准。
按业务模块拆分，每个单元只修改自己的模块及对应测试。
不要修改公共日志实现、依赖版本或锁文件。
保留现有日志级别与业务字段，不增加敏感信息。

先给出拆分方案，列出每个单元的文件范围、依赖和测试方式。
如果某个单元依赖尚未完成的公共修改，请单独列出。
等待我确认方案后再执行。

每个 PR 说明改动范围、验证结果，以及仍需人工确认的问题。

请把路径和规则文件替换成你的项目实际内容。这里的重点是把范围、公共依赖、禁止改动的部分和验收方式写清楚。

/batch 自带方案确认步骤，但你仍要认真检查方案。可以重点看：有没有两个单元改同一份公共文件、是否存在隐含的合并顺序、是否把尚未确定的设计问题分发给了执行代理。

发现问题时，先让它调整方案，再批准执行。

五、worktree 隔离之后，仍然需要合并验收

worktree 能让不同代理在各自的工作目录里编辑代码，减少直接覆盖彼此文件的问题。

它不会自动解决语义冲突。例如，一个 PR 调整函数的返回格式，另一个 PR 仍按旧格式读取；Git 可能顺利合并，程序却不能正常工作。

worktree 也不是完整的运行环境隔离。不同任务仍可能争用同一个端口、数据库或外部测试账号，测试环境要按项目情况安排。

每个 worktree 都要能独立启动项目并运行测试。确认依赖已安装，必要的环境配置和测试数据已准备好；主目录能运行，不代表新 worktree 已经准备完成。

因此，PR 产出后还有几件事要做：

  1. 看清各 PR 的修改范围，确认没有越过原定边界；
  2. 检查测试是否真正覆盖目标行为，而不只是命令退出成功；
  3. 优先让各 PR 能独立合并；存在公共前置改动时，先完成前置改动，再推进后续批次，并在基线变化后重新验证；
  4. 在合并后的代码上运行集成测试和关键业务检查；
  5. 确认工作已保存、提交和处理完毕后，再清理不需要的 worktree。

这些是你需要安排的收尾工作，不能把“各单元都开了 PR”当成整个迁移已经完成。

六、并行度由审查能力决定

多个代理可以同时写代码，你却未必能同时理解多个 PR 的细节。

如果新 PR 产生的速度持续高于审查、修复和合并的速度，队列就会堆积。越晚合并，越可能与主分支的新变化产生冲突。

不必追求一个通用的并发数字。先选一个范围清楚、容易验收的批次，观察实际成本：

  • 每个 PR 需要多少审查时间；
  • 有多少单元必须返工；
  • 合并后是否出现接口或行为问题；
  • 并行执行是否增加了用量和等待。

如果审查已经跟不上，就缩小下一批的范围。提示词中的并行要求也需要结合实际执行计划核对，不能把自然语言要求当成已生效的硬性并发参数。

自测两题

问题 1： 两个代理分别修改不同文件，就可以放心并行吗？

不一定。还要检查接口、共享配置、数据格式、测试环境和合并顺序。文件独立只解决了一部分问题。

问题 2： 所有子代理都通过测试并创建了 PR，任务就完成了吗？

还没有。需要审查 PR，并在合并后的代码上验证整体行为。各单元正确，不自动保证组合之后正确。

本课小结

/batch 适合规则明确、可以拆成独立单元、结果能够验收的跨模块改动。

用它之前，先确定共同规则；批准方案时，检查任务边界；PR 产出后，继续完成审查和集成验证。

把任务拆得独立，比把代理开得更多更重要。
