我在最初的 Day 1 实验里写了三组 top_p，想看看不同参数会生成什么店名。

终端依次打印 0.1、0.5、1.0，看起来实验正在正常进行。后来检查代码才发现：变的只是日志，发给模型的请求根本没带这个参数。

这节课就从这个错误开始。我们不只看模型回答了什么，还要确认三件事：

  • 想改的参数，有没有真正发出去？
  • 模型这次处理了多少 Token？
  • 要等多久才能看到文字，多久才能收齐回答？

完成环境准备篇后，就可以运行本课。仍用本地 qwen3.5:9b，不增加第三方依赖。

一、先查请求，再比较回答

原来的循环大致是这样：

for cfg in configs:
    print("top_p =", cfg["top_p"])
    result = run_inference(
        prompt,
        temperature=cfg["temperature"],
    )

top_p 被打印了出来，却没有传给 run_inference()。函数内部也只把 temperature 放进模型请求。

假如这几次回答不同，我很容易把差异归因于 top_p。但请求没有变，这个结论从第一步就站不住。

本课把构造请求单独写成函数，让参数去向一眼可见。下面只展示 core.py 中与参数传递有关的部分，其余固定设置暂时省略；运行时使用仓库里的完整版本：

def build_request(model, prompt, *, temperature=0.8,
                  top_p=0.9, stream=False):
    return {
        "model": model,
        "messages": [{"role": "user", "content": prompt}],
        "stream": stream,
        "options": {
            "temperature": temperature,
            "top_p": top_p,
            # 其余固定设置见完整代码
        },
    }

这次，两个参数都明确进入了 options。发送的请求也会收录在实验报告中。离线测试还会检查 HTTP 请求中的实际字节，避免出现“保存对了，发送时又漏了”的问题。

模型会把文字拆成小片段来处理，这些片段叫 Token。一个片段可能是一个字、一个词，也可能只是词的一部分。下面几个参数会用到这个单位。

设置 用来做什么
temperature 调整模型选择后续内容时的随机程度；不是答案正确率的开关
top_p 限制下一步从哪些 Token 中选择，下面用一个例子说明
num_ctx 设置本次可容纳的 Token 数，本课为 4096；输入和生成的内容共同占用这份空间
num_predict 限制最多生成多少 Token，本课固定为 256
seed 固定随机种子，方便在同一条件下比较，本课设为 42

例如，假设模型下一步有四个候选片段，概率分别是 60%、25%、10%、5%。只看 top_p 这一步筛选，设为 0.8 时，前两个片段的概率加起来达到 85%，就保留这两个供后续选择。它不是“保留 80% 的词”，也不表示答案有 80% 的概率正确。

完整代码还固定了几项设置：top_k=40、min_p=0 用于候选片段筛选；think=False 请求关闭思考模式；keep_alive="5m" 让模型在请求结束后继续驻留 5 分钟，方便接着实验。它不是回答的超时时限。完整参数含义可以按需查 Ollama 参数说明。现在不用把每个参数都背下来，先知道自己在比较什么。

还有一个区别：确认参数进入请求，不等于证明某个模型内部一定按预想的方式使用了它。 所以接下来仍要实际运行并查看结果。

先进入配套项目目录。如果还没下载代码，从代码仓库获取；已经下载的读者更新后继续。本课目录是 lessons/l01_token_inference/。

先运行默认模式：

默认预览只打印采样实验的 8 条请求，不调用模型，也不包含后面的计时实验。输出较长，可以先看 rows 中第一条的 request.options，确认 temperature、top_p 与这条记录的 case 一致。

确认后运行参数实验：

问题固定为：

给一家修理旧物的小店起一个中文名字，只写名字，不要解释。

程序做两组比较：改 temperature 时固定 top_p=0.9；改 top_p 时固定 temperature=0.8。每组配置各跑两次，第二轮调换高低值的先后顺序。先另外预热一次，不把预热结果放进对照表。

下面是 2026 年 9 月 11 日的实际结果：

改哪个参数 取值 第一次回答 第二次回答
temperature 0 拾光修物 拾光修物
temperature 0.8 时光修补铺 时光修补铺
top_p 0.1 拾光修物 拾光修物
top_p 0.9 时光修补铺 时光修补铺

两组对照的高值其实是同一组设置：temperature=0.8、top_p=0.9，作为两组共用的基线。表中的两行分别实际运行了两次，并非把同一次结果填了两遍；因此四行对应三组不同配置。

这次，temperature=0 和 top_p=0.1 都得到了“拾光修物”。前者选择概率最高的候选；后者缩小候选范围，如果最高概率的候选已经达到 0.1，这一步也只剩它可选。这可以帮助理解两种设置为什么可能得到相同答案，但报告没有记录每一步的候选概率，不能据此认定本次两种设置的选择过程完全一样。

这是固定种子下的一次小样本观察，不代表其他问题也会如此。两个店名哪个更好，表格同样回答不了。

注意，temperature=0.8 的两次回答也一样。我们固定了随机种子，重复运行的目的是看相同条件下的表现，并不是在抽样统计模型能想出多少种名字。不能只凭这两次结果说“温度高就一定每次都不同”，也不能承诺换电脑、换模型版本仍然逐字相同。

本次使用 M1 Pro、16GB 统一内存，Python 3.13.7、Ollama 0.34.0。报告保留了模型摘要和全部请求设置，后面比较结果时能查回当时的条件。

三、Token 数从哪里看

前面提到的文字片段，会按模型使用的词表转换成编号。模型接收的是这些编号组成的序列，统计 Token 用量时数的也是序列中的项数。

因此，len(text) 得到的字符数，不能直接当作 Token 数。同一句话用不同模型的编码方式切分，数量也可能不同。

原 Day 1 代码用 tiktoken 的 cl100k_base 编码重新计算输入和回答的长度。这个工具可以帮助观察文字如何切分，但它算出的是指定编码下的数量，不是本地 Qwen 模型报告的用量。只计算提示词，还会漏掉消息角色等请求格式带来的内容。

本课不另装分词器，直接保留 Ollama 返回的两个字段：

usage = {
    "prompt_eval_count": final.get("prompt_eval_count"),
    "eval_count": final.get("eval_count"),
}
  • prompt_eval_count：服务报告的输入 Token 数。
  • eval_count：服务报告的输出 Token 数。

字段缺失就保留 None，不要用字符数或另一个编码器的结果补进去。

刚才的店名实验里，输入计数都是 31。返回“拾光修物”时，输出计数是 5；返回“时光修补铺”时，输出计数是 4。较短的文字反而对应较大的服务计数，直接按字数估算就会出错。

记录这些数，是为了知道长输入、长回答会让本机承担多少处理工作，也方便以后设置任务用量上限。本课不把 Token 数换算成云 API 费用。

四、先想清楚：你关心哪一种等待

在终端里等三秒后一次看到完整回答，和半秒后先看到一部分、后面继续显示，感觉会不同。只记录总耗时，看不出这个区别。

我们分别记录：

  1. 第一段等待时间：从发出请求，到程序收到第一段非空白正文。
  2. 总等待时间：从发出请求，到收到回答结束标记。

流式返回时，Ollama 会陆续发来一行行 JSON。每一行可能携带一小段文字，最后一条还会带上结束状态和用量信息。程序收到正文后立即打印，不把每个片段都当作一个 Token。

计时部分的关键逻辑如下，省略了报告保存和错误处理：

start = time.perf_counter()
first_content_seconds = None

for body in response_events(base_url, payload):
    elapsed = time.perf_counter() - start
    content = body.get("message", {}).get("content", "")

    if content.strip() and first_content_seconds is None:
        first_content_seconds = elapsed
    if content:
        print(content, end="", flush=True)

    if body.get("done") is True:
        total_seconds = elapsed
        break

perf_counter() 用来计算时间间隔。我们在打印前记下片段到达的时间，所以测到的是“程序何时拿到可以显示的文字”，不是屏幕实际完成绘制的时间。

非流式调用只有一份完整响应，因此在本课的记录方法里，它的第一段等待和总等待相同。空字符串、纯空白以及单独的结束消息，都不算第一段正文。

五、把两种返回方式放在一起跑

执行：

uv run --project lessons --frozen python -m lessons.l01_token_inference --mode timing --output runs/l01-timing-01.json

问题换成：

用中文写三句话，向 Python 初学者解释函数的作用。不要使用代码块。

程序预热一次，再按“非流式、流式、流式、非流式”的顺序运行。输入与生成设置相同，只改变 stream。为了方便比较，这组使用 temperature=0、seed=42。

运行顺序 返回方式 第一段等待 总等待 输出 Token
1 非流式 3.588 秒 3.588 秒 63
2 流式 0.169 秒 3.681 秒 63
3 流式 0.130 秒 3.408 秒 63
4 非流式 4.334 秒 4.334 秒 63

这四次输入 Token 都是 31，回答文字也相同。第一轮流式比非流式更早拿到正文，但总耗时略长；第二轮的总耗时又是流式较短。

所以本次最直接的观察是：流式让程序更早开始显示内容，总耗时则没有固定的胜负。 不要把“第一段来得早”写成“整个回答生成得更快”。

还有一个条件需要留意：第一次对照请求没有命中输入缓存，后面三次报告了 27 个缓存 Token。重复请求时，服务可能复用先前处理过的一部分输入，省掉部分计算，这就是这里说的输入缓存。预热只让模型先运行一次，并没有把所有请求变成完全相同的缓存状态。不过，两次非流式调用中，命中缓存的那次用了 4.334 秒，反而比未命中的 3.588 秒更久。可见这里的总耗时差不能只用缓存解释。再加上只有四次调用，这张表适合解释等待体验，不适合做模型速度排名。

Ollama 也返回自己的生成、加载耗时，单位是纳秒；报告原样保留。它们和 Python 测到的等待时间范围不同，不能混在同一列里比较。

六、打开报告，看一次完整记录

两个 JSON 文件都保存在 runs/。挑一条 rows 记录，顺着看：

位置 看什么
request 实际模型名、问题、stream 和 options
text 拼接后的完整回答
usage Ollama 返回的 Token 数和耗时
first_content_seconds 第一段正文何时到达
total_seconds 收到结束标记时的总等待
success、error 是否完整结束，失败原因是什么

如果缺少结束标记，程序会保留已经收到的内容，但不把它算成成功。生成达到长度上限也会明确标记，后面的请求随即停止，不自动重试。

报告文件不覆盖。再做一次实验时，把文件名中的 01 改成 02。遇到超时先检查 Ollama 和本机负载；Python 停止等待，不表示模型一定已经停止计算。

自己改一次，再解释结果

如果环境准备时安装了其他本地型号，可以在运行命令末尾加 --model 你的模型名，名称以 ollama list 为准。换型号后需要重新观察结果，本文数字只对应本次实测的 qwen3.5:9b。

这次练习先不换模型，只把 --repeats 改为 3，各多做一轮。对着新报告回答：

  • 每次真正发出的参数，是否与想改的一致？
  • 同一段输入，服务报告的输入计数是否相同？
  • 最早看到正文的那次，是否也是最早结束的那次？

答案不必与本文相同，关键是能指出报告中的依据。
