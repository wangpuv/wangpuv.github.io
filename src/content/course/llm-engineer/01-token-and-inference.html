上一篇，我们装好 Ollama，让 Python 收到了本地模型的回答。

程序能运行了，但看着返回的文字，很容易冒出几个问题：同一个问题再问一次，答案为什么可能不同？回答是一下子生成的，还是一点点生成的？一段很短的文字，模型处理起来也一定很短吗？

这些问题都与模型生成文字的过程有关。这一课先把这个过程讲清楚，再动手调整参数、查看用量，并比较两种返回方式的等待时间。

一、先看一次简单的问答

我们请模型给一家小店起名：

给一家修理旧物的小店起一个中文名字，只写名字，不要解释。

在本课的一次实际运行中，本地 qwen3.5:9b 返回了：

拾光修物

从程序这一侧看，我们发出问题，收到回答。问题放在请求的 messages 中，回答文字则出现在响应的 message.content 中。先只看这两处，下面是数据结构的节选，不是一份完整运行脚本：

# 发给模型的问题
messages = [
    {"role": "user", "content": "给一家修理旧物的小店起一个中文名字，只写名字，不要解释。"}
]

# 收到响应后，取出回答文字
answer = response["message"]["content"]

role="user" 表示这条消息来自提问的人，content 就是提问内容。响应里除了正文，还会带有用量和耗时等信息，后面再看。

现在先把目光从 Python 字典移到模型内部：这四个字是怎样生成的？

二、Token 是什么，模型怎样接着往下写？

Python 可以直接用字符串表示一句话，模型计算时用的却是数字。

文字要先经过一个叫分词器的工具，转换成一串编号。每个编号对应词表中的一个片段，这种处理单位叫 Token。它可能对应一个字、一个词，也可能只是词的一部分；空格和标点也参与编码。

可以把这个过程先理解成：

输入文字 → 分词器转换成 Token 编号 → 模型计算
模型生成 Token 编号 → 转回文字 → 显示给用户

这里不能简单规定“一个汉字就是一个 Token”。不同模型使用的词表和切分方式可能不同，同一段话得到的数量也可能不同。Python 的 len(text) 数的是字符，不能直接拿来当模型的 Token 用量。

生成回答时，模型也不是先写好整篇文章再拆开。对本课这种文本生成任务，可以先理解为一个反复进行的过程：

  1. 根据问题和已经生成的内容，计算下一步各种 Token 的可能性。
  2. 按当前的选择规则，选出一个 Token，接到已有内容后面。
  3. 带着新内容继续计算，直到结束，或达到程序设置的长度上限。

例如，“今天的天气很”后面可以接“好”，也可能接“冷”。这里只是用完整的字帮助理解候选内容，并不是某个模型的真实分词结果或概率记录。

每次新接上的内容，都会影响后续选择。因此，同一个问题如果在某一步选了不同的片段，后面的回答也可能逐渐不同。

模型为某段内容给出较高概率，表示它更倾向于这样续写，并不表示这段内容一定符合事实。以后让模型查资料、做计算时，程序仍需要检查依据和结果。

一次可以放进多少内容？

模型本次能够容纳的 Token 数量有限，这个容量通常叫上下文窗口。问题、消息格式以及已经生成的内容，都需要占用空间。

本课把 num_ctx 设为 4096，表示使用 4096 Token 的上下文容量；把 num_predict 设为 256，限制最多生成 256 个 Token。前者像本次可用的总空间，后者限制回答最多写多长，并不是要求回答一定写满 256 个。

这两个设置先保持不变。我们接下来只观察：每一步从候选内容中怎样选择，会怎样影响回答。

三、为什么同一个问题可能得到不同回答？

模型已经算出了候选内容的概率，接下来不一定总挑最高的那个。按概率做选择的过程，叫采样。

本课比较两个参数：temperature 和 top_p。名字可以暂时记不牢，先看它们分别改变什么。

temperature：改变候选内容之间的概率差距

temperature 通常译为“温度”，不是电脑的温度。

较低的正数温度会让选择更集中在高概率候选上；温度升高，则会让原本概率较低的候选更有机会被选中。本课使用的 temperature=0 按最高概率候选进行选择。

这能影响回答的变化程度，却不能直接设置“创意有多少”或“正确率有多高”。温度高时仍可能重复，温度低时也可能反复给出同一个错误答案。

top_p：缩小参与选择的候选范围

假设某一步只有四个候选片段，概率从高到低分别是：

候选片段 概率
A 60%
B 25%
C 10%
D 5%

只看 top_p 这一步筛选：设为 0.8 时，从最高概率开始累加。A 的 60% 还不够，加上 B 达到 85%，于是保留 A、B，后续只在它们之间选择。设为 0.1 时，A 自己已经超过门槛，候选范围就只剩 A。

所以，top_p=0.8 不是“保留 80% 的词”，也不是“答案有 80% 的概率正确”。它使用的是概率加起来达到多少这个门槛。

两者的区别是：温度调整概率之间的差距，top_p 决定保留多大的候选范围。做对照实验时，一次只改变其中一个，才能知道自己在观察什么。

四、动手比较之前，确认参数真的发出去了

比较参数时，有一种很容易忽略的错误：终端打印了不同的值，发出的请求却没有改变。比如下面这段代码，top_p 只出现在打印语句里，调用函数时没有传进去。

print("top_p =", cfg["top_p"])
result = run_inference(prompt, temperature=cfg["temperature"])

如果函数内部也只把 temperature 放进请求，即使几次回答不同，也不能归因于 top_p，因为它根本没有改变。

Ollama 的采样参数要放进请求的 options。本课代码中，与这两个参数有关的部分如下，其余固定设置省略：

"options": {
    "temperature": temperature,
    "top_p": top_p,
}

接下来打开 02_sampling.py。ask() 中写着实际发送的请求，compare() 中列出要比较的配置。程序在每次调用前打印同一份请求中的 options，你可以对照检查参数与值。

五、一次问答处理了多少 Token？

现在我们知道 Token 是模型处理内容的单位，就可以看一次问答的输入和输出各有多少了。

记录用量，是为了判断程序每次让模型处理了多长的内容。以后加入整篇资料、历史对话或连续工具调用，输入和输出都会增加；这些数能帮助我们检查是否接近容量限制，以及任务用量增长在哪里。

Ollama 在回答结束时提供两个计数字段。代码只需从最终响应中取出它们：

input_tokens = final.get("prompt_eval_count")
output_tokens = final.get("eval_count")

prompt_eval_count 是服务报告的输入 Token 数，eval_count 是输出 Token 数。这里用 .get()，字段缺失就得到 None，不会把“没收到计数”误记成零。

刚才的店名实验中，输入计数都是 31。“拾光修物”对应的输出计数是 5，“时光修补铺”对应 4。较短的文字反而对应较大的服务计数，正好说明不能直接按字数推算用量。

你也可能见过用 tiktoken 计算 Token 数的代码。这个工具需要指定编码，例如 cl100k_base；它适合观察该编码怎样切分文字，但不能拿它的结果替代本地 Qwen 的服务计数。只数问题文本，还会漏掉消息角色等格式带来的内容。本课直接保留 Ollama 的返回值，不另装分词器。

六、回答怎样显示，会影响等待的感觉

前面讲过，模型逐步生成内容。但生成一点就显示一点，还是等生成结束后一次显示，是两种不同的返回方式。

非流式会等完整响应返回后再显示。流式则陆续返回片段，程序收到后就可以继续显示。流式片段不保证恰好是一个 Token，不能数片段来计算用量。

比如，同样一段回答，等三秒后一次看到全部，和先看到一部分、后面继续出现，等待的感觉会不同。因此我们分别测量：

  • 第一段等待时间：发出请求后，多久收到第一段非空白正文。
  • 总等待时间：发出请求后，多久收到回答结束标记。

Ollama 请求里的 stream 用来选择返回方式：False 是非流式，True 是流式。打开 03_streaming.py 的 receive()，可以看到请求怎样发送、JSON 怎样逐行读取、文字怎样打印，以及时间怎样记录。程序会依次运行两种返回方式：

uv run --project lessons --frozen python -m lessons.l01_token_inference.03_streaming --output runs/l01-timing-01.json

问题换成：

用中文写三句话，向 Python 初学者解释函数的作用。不要使用代码块。

程序预热一次，再按“非流式、流式、流式、非流式”的顺序运行。输入与生成设置相同，只改变 stream。为了方便比较，这组使用 temperature=0、seed=42。

下面是配套 03_streaming.py 的实测结果：

运行顺序 返回方式 第一段等待 总等待 输出 Token
1 非流式 3.143 秒 3.143 秒 63
2 流式 0.147 秒 3.358 秒 63
3 流式 0.113 秒 3.380 秒 63
4 非流式 3.415 秒 3.415 秒 63

这四次输入 Token 都是 31，回答文字也相同。第一轮流式比非流式更早拿到正文，但总耗时略长；第二轮的总耗时又是流式较短。

所以本次最直接的观察是：流式让程序更早开始显示内容，总耗时则没有固定的胜负。 不要把“第一段来得早”写成“整个回答生成得更快”。

还有一个条件需要留意：第一次对照请求没有命中输入缓存，后面三次报告了 27 个缓存 Token。重复请求时，服务可能复用先前处理过的一部分输入，省掉部分计算，这就是这里说的输入缓存。预热只让模型先运行一次，并没有把所有请求变成完全相同的缓存状态。不过，两次非流式调用中，命中缓存的那次用了 3.415 秒，反而比未命中的 3.143 秒更久。可见这里的总耗时差不能只用缓存解释。再加上只有四次调用，这张表适合解释等待体验，不适合做模型速度排名。

本课的时间由 Python 在收到内容后、打印之前记录，测的是程序何时拿到文字，不是屏幕实际绘制的时间。非流式只有一次完整响应，因此记录中的第一段等待和总等待相同。

运行之后，自己看一次结果

三个脚本的报告都保存在 runs/ 下。打开文件，先找 rows，再选其中一条记录。问答和采样脚本把请求放在 request，原始回答与用量放在 response；流式脚本则另有拼接后的 text、usage 和两个等待时间。具体字段位置见运行说明，不必一下读懂全部原始响应。

再做一次时，把输出文件名里的 01 改成 02，已有文件不会被覆盖。运行第二、第三个脚本时，可以加 --repeats 3 多做一轮，再看看：同样的设置是否仍得到相同回答？最早收到正文的那次，是否也最早结束？

如果安装的是其他本地型号，在命令末尾加 --model 你的模型名，名称以 ollama list 为准。本文数字只对应本次实测型号，更换后需要重新观察结果。
