本课回答三个问题：/effort 和 /fast 分别控制什么、怎样选择 effort 档位、什么时候值得为快速模式付费。

适合：已经会选择模型和权限模式，开始关心 Claude Code 的响应质量、等待时间与使用成本的人。

📌 基于 Claude Code 官方文档与本机 Claude Code 2.1.223 核对至 2026 年 8 月。模型、价格和功能可用性变化很快，具体以当前版本的 /effort、/fast 与官方文档为准。

一句话心智模型

/effort 决定“想多深”，/fast 决定“多快把结果送回来”。

它们不是同一个速度开关，而是两个相互独立的旋钮：

  • /effort 作用在模型推理层：档位越高，Claude 越愿意在复杂步骤上投入更多思考；
  • /fast 作用在服务速度层：模型能力不变，用更高的每 token 价格换更低的响应延迟；
  • /model 负责选择模型，和前两个设置可以组合使用。

所以，快速模式不会让 Claude “少想一点”；降低 effort 才可能用更少的推理换速度和成本。

一、/effort：调节推理强度

effort 不是固定的 thinking token 数字，而是控制自适应推理投入程度的偏好。

Claude 会根据每一步的难度决定要不要展开思考，而 effort 决定它可以有多积极：

  • 简单任务即使使用高档位，也不一定强行进行很长的推理；
  • 复杂任务如果使用低档位，Claude 可能更快作答，但也更容易遗漏边界条件；
  • 同名档位会按模型分别校准，不能认为不同模型的 high 完全等价。

1. 五个模型 effort 档位

档位 适合什么 使用建议
low 重命名、搜索、格式整理、明确的小修改 只给范围小、不依赖复杂判断的任务
medium 日常函数编写、小型重构、成本敏感任务 可以接受少量能力折中的常规工作
high 调试、代码审查、多文件修改 大多数需要认真判断的任务从这里开始
xhigh 复杂 agentic 编码、深度重构、架构分析 需要更深推理、能接受更多 token 时使用
max 极难问题、系统设计、长期未解的 bug 临时使用，先验证收益是否值得成本

并不是所有模型都支持五档：

  • Fable 5、Opus 5、Sonnet 5、Opus 4.8、Opus 4.7：支持 low 到 max，包括 xhigh；
  • Opus 4.6、Sonnet 4.6：不支持 xhigh，设置后会回落到 high；
  • 其他没有列出的模型不支持 effort。

当前支持 effort 的模型默认都是 high，只有 Opus 4.7 默认是 xhigh。

2. 哪些档位会被记住

low、medium、high、xhigh 在交互式会话中设置后会跨会话保留。

max 默认只在当前会话生效，退出后不会作为长期设置保存。只有通过环境变量设置时，它才会在新会话中继续生效。

这是一种有意的保护：最激进的推理档位不应该在你忘记之后一直消耗更多 token。

3. ultracode 不是第六个模型档位

/effort 菜单里还可能看到 ultracode，但它和前面五档不是同一类东西。

ultracode 是 Claude Code 层的会话设置：

  • 向模型发送 xhigh；
  • 对有分量的任务启用动态工作流编排；
  • 让 Claude 根据任务情况组织计划、执行、检查和修订；
  • 只在当前会话生效。

可以这样理解：

  • low 到 max 调节一次推理愿意想多深；
  • ultracode 还会改变复杂任务的组织方式。

如果动态工作流不可用，ultracode 只会退化为 xhigh。

4. ultrathink 只给当前一轮加力

如果只想让某个问题多想一层，不必修改整段会话的 effort。

在提示词中加入：

ultrathink

Claude Code 会为这一轮加入更深入思考的上下文指令，但发送给 API 的 effort 档位不会改变。

当前只有 ultrathink 是特殊关键词；think、think hard、think more 只会作为普通提示词传入。

二、怎样设置 /effort

最直接的方式是：

/effort

不带参数会打开交互式选择器。也可以直接指定档位：

/effort low
/effort high
/effort xhigh
/effort max
/effort auto

auto 表示回到当前模型的默认档位。

其他入口还有：

  • 在 /model 选择器中用左右方向键调节；
  • 启动时传入 claude --effort high；
  • 在设置文件中写入 effortLevel；
  • 通过 CLAUDE_CODE_EFFORT_LEVEL 环境变量强制指定；
  • 在 skill 或子代理的 frontmatter 中设置 effort。

frontmatter 示例

---
name: security-reviewer
description: "检查认证、授权与敏感数据处理"
tools: Read, Grep, Glob
model: opus
effort: high
---

这样可以让安全审查子代理固定使用 high，不必要求整个主会话都保持同一档位。

设置优先级

可以先记住这条主线：

环境变量 > 已配置档位 > 模型默认值

skill 和子代理的 frontmatter 会覆盖会话档位，但不能覆盖环境变量。

另外，settings.json 的 effortLevel 只接受 low、medium、high、xhigh。max 和 ultracode 都不适合作为普通持久化档位。

一个容易忽略的成本：切换档位会重建缓存

模型和 effort 都属于提示缓存的键。

一段对话开始后再切换 /effort，下一次请求需要重新读取完整上下文。Claude Code 会在应用这类变更前提示你确认。

因此，模型和 effort 最好在会话开头选好，不要在长对话中反复切换。

三、/fast：用更高价格换更低延迟

快速模式不是另一个模型，也不会主动减少推理步骤。

它使用支持快速模式的同一 Opus 模型，通过速度优先的 API 配置降低响应延迟，最高可达到约 2.5 倍速度。模型的能力和质量不因此改变，但每 token 价格更高。

1. 当前支持哪些模型

截至本课核对时间，快速模式支持：

  • Opus 5；
  • Opus 4.8。

它不支持 Sonnet、Haiku、Fable 和其他 Opus 版本。Opus 4.7 的快速模式已经在 2026 年 7 月移除。

在 Claude Code 2.1.219 及以后版本中，快速模式默认使用 Opus 5。

2. 怎样开关

在 Claude Code CLI 中输入：

/fast

然后按 Tab 切换开关。再次运行 /fast 可以查看并改变当前状态。

开启后，提示栏会出现 ↯ 图标。如果当前不是支持快速模式的模型，Claude Code 会自动切换到 Opus。

关闭快速模式后，模型仍然停留在 Opus；要换回其他模型，需要使用 /model。

快速模式目前只支持 Claude Code CLI，不支持 VS Code 扩展。

3. 成本怎样计算

当前 Opus 5 和 Opus 4.8 的快速模式价格相同：

模型 输入价格 / MTok 输出价格 / MTok
Opus 5 $10 $50
Opus 4.8 $10 $50

对 Pro、Max、Team、Enterprise 订阅用户，快速模式从 usage credits 计费，不计入订阅套餐的使用限额。

这意味着：即使套餐额度还没有用完，快速模式也会从第一个 token 开始消耗 usage credits。没有开启 usage credits 时，/fast 无法使用。

快速模式只适用于 Anthropic API 和 Claude 订阅，不支持 Amazon Bedrock、Google Cloud Agent Platform、Microsoft Foundry 和 Claude Platform on AWS。Team 与 Enterprise 组织还需要 Owner 先在管理设置中启用该功能。

4. 为什么要在会话开头开启

一段对话第一次打开快速模式时，快速模式请求头会改变缓存键。

下一次请求需要按快速模式价格重新读取整段已有上下文，而且这部分是未缓存输入。对话越长，首次切换的成本越高。

例如，已有 40 万 token 的上下文，按 $10 / MTok 的快速输入价格估算，仅这次完整重读就约为 4 美元。

这笔成本在同一段对话里只发生一次。之后关掉再打开不会重复，因为速度设置本身不再改变缓存键；但 /clear 和 /compact 会重新开始计算。

所以最实用的规则是：

决定要用 fast，就在会话刚开始时打开。

5. 快速模式默认会跨会话保留

交互式会话中打开快速模式后，它默认会在后续会话继续保持开启。

这很方便，也容易让人忘记自己一直在消耗 usage credits。

如果希望每个会话都重新确认，可以在设置文件中加入：

{
  "fastModePerSessionOptIn": true
}

这样每个新会话都会从关闭状态开始，需要时再手动执行 /fast。

四、两个旋钮怎样组合

不要把“速度”当成一个维度。真正要判断的是两个问题：

  1. 这个任务需要多深的推理？
  2. 我现在对等待时间有多敏感？
任务场景 effort fast 原因
批量重命名、格式整理、明确的小修改 low 通常关 任务简单，降低 effort 已经够快
日常开发、小型重构 medium / high 关 默认速度和成本更均衡
代码审查、疑难调试、多文件重构 high / xhigh 通常关 优先保证判断质量
架构设计、极难 bug xhigh / max 关 深度优先，等待通常不是主要成本
有分量的自主构建任务 ultracode 关 让动态工作流组织复杂执行过程
你盯着终端进行实时调试 medium / high 可开 每轮等待会直接打断思路
紧急且复杂的交互任务 xhigh 可开 深度和低延迟都要，代价是更贵
/loop、CI、后台长任务 按需 关 机器等待通常不值得支付速度溢价

low + fast 会发生什么

这是“简单任务追求最低延迟”的组合。

较低的 effort 减少复杂推理，fast 再降低输出延迟。适合你正在实时盯着终端、需要快速完成大量明确小步骤的场景。

但如果任务本身不急，只用 low 往往已经足够，没必要再支付快速模式溢价。

max + fast 矛盾吗

不矛盾。

max 要求模型尽可能深入思考，fast 要求服务更快地完成同样的推理和输出。两者可以同时成立。

真正的问题是成本：更多 thinking token 再乘上快速模式的高单价，很容易成为最贵的组合。

因此，是否使用它取决于“节省的等待时间”是否真的比额外成本更重要，而不是两个设置在机制上冲突。

五、一套实用决策法

开始任务前，可以按下面三步判断。

第一步：先按任务难度选 effort

  • 机械、明确、范围小：low；
  • 常规开发：medium 或 high；
  • 调试、审查、跨文件改动：high 或 xhigh；
  • 极难问题：临时使用 max；
  • 需要动态编排复杂执行：ultracode。

第二步：再判断“人在不在等”

  • 人正在盯着终端、需要高频来回：考虑 fast；
  • Claude 在后台跑，晚几分钟没有影响：关闭 fast。

第三步：在会话开头设定

先选 /model，再选 /effort，最后决定是否打开 /fast。

这样既能避免在长上下文中重建缓存，也不容易因为反复切换而失去对成本的判断。

六、避坑清单

  • [ ] /effort 调推理强度，/fast 调服务延迟，不要把两者混成一个速度开关。
  • [ ] xhigh 不是所有支持 effort 的模型都有；不支持时会回落到 high。
  • [ ] max 只在当前会话生效，不会作为普通配置长期保存。
  • [ ] ultracode 是 Claude Code 的工作流设置，不是第六个模型 effort 档位。
  • [ ] 单轮想多一点用 ultrathink，整段会话改变强度才用 /effort。
  • [ ] 模型和 effort 最好在会话开头选好，切换会触发缓存重建。
  • [ ] 快速模式当前只支持 Opus 5 和 Opus 4.8。
  • [ ] 快速模式只支持 CLI，不支持 VS Code 扩展。
  • [ ] 订阅用户使用 fast 会直接消耗 usage credits，不走套餐内额度。
  • [ ] 第一次在长对话中开启 fast 会按快速价格完整重读已有上下文。
  • [ ] fast 默认跨会话保留；担心忘关时设置 fastModePerSessionOptIn: true。
  • [ ] 后台任务和 CI 通常不值得为更低延迟支付溢价。

本课小结

Claude Code 的速度、质量和成本，不是靠一个开关决定的。

更准确的控制方法是：

  1. 用 /model 选择能力底座；
  2. 用 /effort 按任务难度调节推理强度；
  3. 只在人的等待成本真的很高时使用 /fast；
  4. 在会话开头完成设置，避免长上下文重建缓存；
  5. 复杂任务优先保证推理质量，后台任务优先控制成本。

先问任务需要想多深，再问结果需要多快回来。两个问题分开，选择就会清楚很多。
