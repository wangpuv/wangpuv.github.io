本课回答三个问题：什么时候应该派子代理、当前版本怎样创建和调用子代理、什么时候才值得接入 MCP。

适合：主会话经常被搜索结果、测试日志淹没，或者希望 Claude Code 读取工单、监控、数据库等外部系统的人。

📌 基于 Claude Code 官方文档与本机 Claude Code 2.1.221 核对至 2026 年 8 月。产品更新较快，具体行为以官方文档与 /release-notes 为准。

一句话结论

子代理和 MCP 都是在给 Claude Code 扩展能力，但扩展的方向不同：

子代理：增加分工，把支线放进独立上下文
MCP：增加连接，让 Claude 够到外部工具和数据

可以把它们记成一句话：

子代理管“谁来做”，MCP 管“能用什么做”。

两者还可以组合：让一个权限受限的子代理，只连接完成任务必需的 MCP server。

一、先分清几种容易混淆的 agent

Claude Code 里的“agent”现在不只一种。如果不先分清，后面很容易把命令和能力混在一起。

名称 谁协调 是否独立上下文 适合情况
子代理（subagent） 主会话里的 Claude 是 支线搜索、测试、日志分析、专项审查
后台 agent session 你 是，完整会话 多个独立任务并行，之后人工查看
Agent team team lead 每个成员独立 需要成员共享任务并互相通信；目前仍属实验功能
产品里的 agent 你的应用 由产品架构决定 面向终端用户运行的业务逻辑

本课重点是第一种：同一个 Claude Code 会话里的子代理。

还有两个长得很像的入口：

/agents        → 当前版本只提示你让 Claude 创建，或直接编辑 agent 文件
claude agents  → 打开 agent view，管理多个后台会话

它们不是同一个东西。

二、子代理到底隔离了什么

子代理拥有自己的上下文窗口。它会在那里面读取文件、搜索代码、运行命令，完成后把结果交回主会话。

这意味着：

  • 大量搜索结果、测试日志和中间试错留在子代理里；
  • 主会话通常只接收最后的报告；
  • 多个相互独立的调查可以并行进行；
  • 子代理可以使用不同的模型、工具和权限设置。

但“独立上下文”不等于“什么都看不到”。普通子代理启动时通常会得到：

  • 自己的系统提示词；
  • 主会话为这次委派整理的任务说明；
  • 主会话会加载的 CLAUDE.md 层级与项目规则；
  • 会话启动时的 Git 状态快照；
  • 通过 skills 字段预加载的技能。

内置的 Explore 和 Plan 是例外：为了保持轻量，它们不会加载 CLAUDE.md 和 Git 状态。

上下文隔离不等于文件隔离

普通子代理默认仍从主会话的当前工作目录开始，看到的是同一套磁盘文件。

所以：

  • 两个 agent 同时改同一文件，仍可能互相覆盖；
  • 子代理执行的文件修改，会真实落到当前工作区；
  • 真正需要独立 checkout 时，应在定义里设置：
isolation: worktree

这会让子代理在临时 Git worktree 中工作，而不仅仅是换一个上下文窗口。

但它不是主会话工作区的完整复制品。临时 worktree 默认从仓库的默认分支创建，不等于复制主会话当前的 HEAD；主工作区里的未提交改动也不会自动出现。委派前要先确认子代理能看到完成任务所需的代码。

三、当前版本怎样创建子代理

旧版教程常写：

/agents → Create new agent → Select tools

这条路径已经过时。从 Claude Code 2.1.198 起，/agents 不再打开创建向导。

现在推荐两种方式：

  1. 直接告诉 Claude 想要什么 agent、放在哪个作用域；
  2. 手动创建 Markdown 定义文件。

两个最常用的保存位置

位置 范围 是否适合提交到 Git
.claude/agents/ 当前项目 适合，团队可以共享
~/.claude/agents/ 这台机器上的所有项目 不进入项目仓库，适合个人通用 agent

还可以使用 --agents 在启动时传入 JSON，定义只在当前会话生效；插件也可以自带 agent。

一个真正只读的 reviewer

在项目中创建：

.claude/agents/code-reviewer.md

内容如下：

---
name: code-reviewer
description: 审查最近的代码改动，发现正确性、安全性与可维护性问题。完成代码修改后主动使用。
tools: Read, Grep, Glob
model: sonnet
---

你是一名只读代码审查员。

先读取相关代码，以及主会话明确提供的 diff，再按严重程度报告问题。
每条问题必须说明文件位置、风险与建议，不要修改文件。

这里有两层约束：

  • tools 是硬边界：没有 Edit、Write 和 Bash，就无法调用这些工具；
  • 正文里的“不要修改文件”是行为说明，帮助模型理解角色。

真只读要靠工具层限制，不能只靠提示词里的承诺。

如果省略 tools，子代理会继承它可用的工具池，而不是默认只读。

改完是否要重启

当前版本会监视已经存在的 .claude/agents/ 与 ~/.claude/agents/ 目录，新增或修改文件后通常几秒内即可生效。

只有两类常见情况需要重启：

  • 会话启动时，这个 agents 目录还不存在；
  • 会话使用了 --disable-slash-commands，不会监视这些目录。

因此，“每次修改 agent 都必须重启”也已经不是当前版本的准确说法。

四、三种调用方式

1. 让 Claude 自动判断

Claude 会结合当前任务与 agent 的 description 决定是否委派。

所以 description 不应只写“代码审查员”，而要写清：

  • 它负责什么；
  • 什么时候使用；
  • 什么时候不要使用。

例如：

description: 审查最近的代码改动，发现正确性、安全性与可维护性问题。完成代码修改后主动使用。

2. 显式点名一次

在输入框键入 @，从补全列表中选择 agent，就能保证它执行这次任务。

也可以手动输入：

@agent-code-reviewer 检查这次认证模块的改动

对于插件提供的 agent，名称可能带插件命名空间。

3. 整个会话都使用这个 agent

claude --agent code-reviewer

这不是“派出一个支线”，而是让主线程本身使用该 agent 的系统提示词、工具限制和模型。

适合需要强制固定角色的专用会话。

五、什么时候派子代理才划算

子代理不是免费的。它需要建立自己的上下文，并重新读取完成任务所需的材料。

最适合委派的任务通常具备三个特点：

输入小 + 过程脏 + 输出小
  • 输入小：不用把主会话的大量历史重新讲一遍；
  • 过程脏：会产生很多搜索结果、日志或试错记录；
  • 输出小：最后只需要一份结论或清单。

典型例子：

  • 跑完整测试，只汇报失败项；
  • 搜索一个模块的调用链，只返回关键路径；
  • 分析一大段日志，只给出根因和证据；
  • 分别调查认证、数据库、API 三个互不依赖的区域。

不适合的情况：

  • 只改一个明确的小地方；
  • 任务需要频繁来回确认；
  • 规划、实现和测试共享大量上下文；
  • 为了一个简单动作，需要把整份设计文档重新喂一遍。

原稿实验中曾观察到一次子代理运行显示 13.0k tokens。这个数字可以提醒我们“子代理有成本”，但它只是一次特定版本、模型和任务下的观测，不是固定启动税，也不是官方保证值。

六、模型、记忆与后台运行

模型怎么选

model 可以填写：

  • inherit
  • haiku
  • sonnet
  • opus
  • fable
  • 具体的完整 model ID

省成本的搜索和整理可以考虑较轻的模型；复杂审查与推理使用更强模型。实际可用范围仍取决于账号订阅、组织策略和模型开放情况。

记忆怎么选

通过 memory 字段可以让自定义子代理跨会话保存经验：

值 路径 适合情况
user ~/.claude/agent-memory/<agent>/ 跨项目的个人经验
project .claude/agent-memory/<agent>/ 项目知识，适合团队共享
local .claude/agent-memory-local/<agent>/ 项目知识，但只保留在本机

不写 memory，就是不启用持久化 agent 记忆。

无状态代码审查器通常不需要记忆：每次只审当前 diff，历史印象反而可能影响判断。

还要注意：启用 agent memory 后，Claude Code 会让子代理拥有管理记忆文件所需的 Read、Write 和 Edit 能力。如果目标是严格的“完全不写”，不要给它开启持久记忆。

前台与后台

当前版本通常会让子代理在后台运行；如果主会话必须拿到结果才能继续，也可能以前台方式运行。

  • 前台：主会话等待结果；
  • 后台：你可以继续工作，完成后收到通知；
  • /tasks：查看、附着或停止当前会话中的后台任务。

这与 claude agents 管理的独立后台会话仍然不是同一层功能。

七、MCP：让 Claude 连接外部系统

MCP 是 Model Context Protocol 的缩写，是模型与外部工具、数据源之间的标准协议。

一个 MCP server 可以向 Claude Code 暴露：

  • Tools：执行查询、创建工单、发送消息、触发动作；
  • Resources：文档、数据库结构、issue 等可读取内容；
  • Prompts：由 server 提供的可复用命令模板。

常见用途包括：

  • 读取 Jira、GitHub issue 或设计稿；
  • 查询 Sentry、监控平台和数据库；
  • 创建工单、草稿或自动化流程；
  • 访问 Claude Code 原生工具无法直接触达的内部系统。

可以把判断标准记成一句话：

MCP 是为了够到 Claude 原生够不着的东西。

本地文件本来就能用 Read、Grep、Glob 读取，就没有必要再绕一层 MCP。

八、怎样添加和管理 MCP server

远程服务优先使用 HTTP：

claude mcp add --transport http <名称> <URL>

本地进程通常使用 stdio：

claude mcp add <名称> -- <命令> <参数>

常用管理命令：

claude mcp list
claude mcp get <名称>
claude mcp remove <名称>

进入 Claude Code 后，运行：

/mcp

可以查看连接状态、重新连接、启用或禁用 server，并为需要 OAuth 的远程服务完成登录。

三种作用域

作用域 加载范围 是否共享 存储位置
local 当前项目 否 ~/.claude.json 中的项目配置
project 当前项目 是 项目根目录 .mcp.json
user 所有项目 否 ~/.claude.json

local 是默认值。带凭证或仍在试验的 server，优先放 local；团队共同使用、且配置中不含秘密的 server，可以考虑 project。

项目级 .mcp.json 来自仓库时，需要先通过工作区信任和 server 审批，不能让仓库自己批准自己。

九、MCP 的上下文成本已经变了

旧版常见说法是：

每接一个 MCP server，它的全部工具定义都会塞进上下文。

当前默认行为已经不是这样。

在支持 Tool Search 的官方默认环境中，Claude Code 会按需发现和加载 MCP 工具：

  1. 会话启动时主要加载工具名称和 server instructions；
  2. 真正需要某项能力时，再搜索并加载对应工具定义；
  3. 只有实际用到的工具进入上下文。

因此，在这类环境中，接入多个 MCP server 的上下文成本已经显著降低。

不过，某些云平台、第三方 API 代理、不支持相关能力的模型，或者显式关闭 Tool Search 的配置，仍可能提前加载 MCP 工具定义。不要把“按需加载”当成所有环境都具备的固定行为。

但“按需加载”不代表可以随便连接：

  • server 仍然扩大了可访问范围；
  • 外部内容可能携带提示注入；
  • OAuth 或 token 代表真实账号权限；
  • 写操作会在外部系统产生真实后果；
  • 工具输出过大仍会消耗上下文。

所以 MCP 的首要成本已经不只是 token，更是信任与权限。

十、把子代理与 MCP 安全地组合

假设你想让 Claude 检查 Sentry 中的错误，但不希望它修改代码，也不希望主会话加载一堆日志。

可以创建一个专用子代理：

---
name: sentry-investigator
description: 调查 Sentry 错误并返回根因、证据和修复建议；不要修改代码。
tools: Read, Grep, mcp__sentry__get_issue, mcp__sentry__list_events
mcpServers:
  - sentry
model: sonnet
---

上面的 MCP tool 名称只是只读工具示例。不同 server 暴露的名称可能不同，应以该 server 的文档和当前 Claude Code 实际暴露的工具名为准，并只列出完成调查所需的读取类工具。不要直接写 mcp__sentry 这种 server 级通配符，否则该 server 的写入类工具也可能一起被放开。

这个组合形成三道边界：

  1. description 决定什么时候派它；
  2. tools 与 mcpServers 决定它能碰什么；这里仅允许两个明确列出的 Sentry 只读工具；
  3. 权限规则与 OAuth 决定具体动作是否允许执行。

示例里的 - sentry 是复用当前会话已经配置的 server。它与“内联配置”不是一回事。

如果希望 MCP server 只在这个子代理运行期间连接，需要在 mcpServers 中写入包含 type、url 或 command 等字段的完整 server 定义。这样的内联 server 会在子代理启动时连接、结束时断开，主会话不必拥有那组 MCP 工具。

这正是最小权限原则：

只给完成这项任务所需的工具、数据和持续时间。

十一、几个容易踩的坑

1. 把 /agents 当成当前版本的管理向导

2.1.198 以后，创建 agent 应让 Claude 写文件或手动编辑 .claude/agents/。

2. 以为独立上下文就是独立文件系统

默认仍共用当前工作区。需要隔离修改时使用 isolation: worktree。

3. 只在正文写“不要修改”

提示词是行为说明，tools 才是能力边界。只读 reviewer 不应获得 Edit、Write 或不必要的 Bash。

4. 开了 memory，却以为它仍然完全不写

agent memory 需要写记忆文件。严格无写入的 agent 不要启用持久记忆。

5. 为了“看起来高级”而接 MCP

原生工具已经够用时，MCP 只会增加连接、信任和权限成本。

6. 把 Tool Search 当成安全机制

Tool Search 只是延迟加载工具定义，不会替你审查 server 是否可信，也不会替代权限规则。

7. 忘记外部系统的写操作是真实的

创建工单、发送消息、修改数据库或触发部署，都不只是聊天里的建议。先用只读权限验证，再逐步开放写能力。

动手练习

练习一：创建只读子代理

  1. 让 Claude 在 .claude/agents/ 创建一个 code-reviewer.md；
  2. 只给它 Read、Grep、Glob；
  3. 用 @ 从补全列表中选择它；
  4. 让它审查一个小 diff；
  5. 检查它是否只返回问题，没有修改文件。

练习二：检查 MCP 作用域

  1. 运行 claude mcp list；
  2. 查看某个 server 的作用域与连接状态；
  3. 进入 Claude Code 后运行 /mcp；
  4. 找出哪些 server 是 local、project 或 user；
  5. 对每个 server 问一句：Claude 原生工具是否已经能完成同样的事？

练习的重点不是“多接几个工具”，而是建立两个判断：

这条支线会不会污染主会话？
这个外部系统是否真的值得开放给 Claude？
