本课回答三个问题：/code-review 和 /review 有什么区别、为什么“让写代码的模型检查一下”还不够、怎样建立一套真正能发现问题的审查流程。

适合：已经会让 Claude Code 写代码，准备把“能跑”提升到“敢合并”的人。

📌 基于 Claude Code 官方文档核对至 2026 年 7 月。产品更新较快，命令和计费细节以官方文档与 /release-notes 为准。

一句话结论

真正的代码审查，不是问刚写完代码的模型一句“有没有问题”，而是：

把真实 diff 交给一双相对独立的新眼睛，让它按明确标准找问题，再逐条验证。

其中有四个关键词：

真实代码 + 改动意图 + 新的审查视角 + 可验证的证据

缺少真实代码，审查会变成讨论方案；缺少新视角，模型容易沿用写代码时的假设；缺少验证，审查意见又可能只是新的猜测。

一、三种审查方式，分别用在什么地方

先记住这张表：

命令 主要对象 深度与位置 适合场景
/code-review 当前分支的真实 diff，也可指定文件、分支、PR 或 ref 范围 本地运行，深度随 effort 调整 写完代码后的提交前自查
/review <PR> 一个 GitHub Pull Request 本地、单次、只读、速度快 审同事或另一个代理提交的 PR
/code-review ultra 当前分支或指定 PR 可用时进入云端多代理审查，并独立验证问题 重要改动合并前的深度把关

1. /code-review：审手头的真实改动

最简单的用法：

/code-review

它默认审查：

  • 当前分支领先 upstream 的提交；
  • 工作区里尚未提交的改动。

也可以显式指定范围：

/code-review high
/code-review high main...feature/auth
/code-review high 123

这里的 low、medium、high、xhigh、max 是审查 effort。低档位更保守，优先报告高置信度问题；高档位覆盖更广，但也可能带来更多需要人工判断的发现。

两个常用参数：

/code-review --fix
/code-review --comment
  • --fix：把审查发现直接应用到工作区；
  • --comment：把发现作为 GitHub PR 的行内评论发出去。

在 Claude Code 2.1.218 及之后的版本中，/code-review 默认在后台子代理中运行，拥有自己的上下文，不会持续占满当前对话。完成后，审查结果会回到当前会话。

注意： 后台审查通过 --fix 写入的改动不在当前会话的 checkpoint 里，/rewind 不能替你撤销。使用 --fix 后要先看 git diff，需要回退时用 Git。

2. /review <PR>：快速通读一个 PR

/review 123

/review 面向已经存在的 GitHub PR，是一次快速、只读的单轮审查。

还可以在 PR 编号后补充关注点：

/review 123 重点检查鉴权边界、并发竞态和回滚兼容性。以代码为准，逐项给出文件与行号。

如果不提供 PR 编号，Claude Code 会列出当前仓库的开放 PR 供你选择。

3. /code-review ultra：重要改动的云端深审

/code-review ultra
/code-review ultra 123

它会把审查放到云端沙箱中，由多名审查代理并行探索，再独立复现和验证候选问题。/ultrareview 目前仍可作为别名，但官方推荐写法已经是 /code-review ultra。

Ultrareview 需要使用 claude.ai 账号登录，并且不支持 Amazon Bedrock、Google Cloud Agent Platform、Microsoft Foundry，以及启用 Zero Data Retention 的组织。如果当前环境无法使用 Ultrareview，/code-review ultra 会退回本地审查。

这更适合：

  • 登录、支付、权限等高风险模块；
  • 跨多个目录的大型重构；
  • 即将合并、希望再做一次深度把关的 PR。

它属于 research preview。Pro 和 Max 当前提供 3 次一次性免费试用，之后通常通过 usage credits 计费；Team 和 Enterprise 没有免费次数。实际价格与资格以启动前的确认窗口为准。

二、为什么不要只让模型审自己

同一个模型刚完成实现时，已经形成了一套解释：

  • 它为什么这样拆模块；
  • 它认为哪些边界不会发生；
  • 它默认哪些调用方会遵守约定；
  • 它为什么觉得当前测试已经够了。

这些解释在写代码时有用，但在审查时也可能成为锚点。模型容易继续沿着原来的思路证明“这套实现是合理的”，而不是主动寻找“原来的思路哪里可能错了”。

因此，审查需要尽量引入新的视角。

三个层级

基础做法：使用 /code-review。

它在独立的后台上下文中审真实 diff，至少不会把整段实现过程原样带进审查。

更稳做法：换会话或换模型。

让日常模型完成实现，再开一个更干净的会话，或者临时切换到更擅长复杂推理的模型审查。

重要改动：换模型家族或使用云端多代理。

如果代码由另一类编码代理生成，可以让 Claude 审；反过来也一样。不同模型家族的训练与推理习惯不同，盲点往往也不同。

这不是说“不同模型一定正确”，而是让错误不容易沿着同一条思路被重复忽略。

三、审真实代码，不要只审总结

这是本课最重要的原则。

总结描述的是：

作者希望自己做了什么

diff 展示的才是：

代码实际上做了什么

只把另一个代理的总结交给 Claude，它只能判断“这个方案听起来是否合理”；只有让它看到真实 diff，它才能发现：

  • 条件分支漏了一条路径；
  • 异常被吞掉；
  • 并发状态存在竞态；
  • 权限检查只放在了前端；
  • 数据迁移无法安全回滚；
  • 测试覆盖了成功路径，却遗漏失败路径。

总结并不是没用。最好的输入是：

真实 diff + 作者意图 + 风险提示

可以复用这段提示：

请审查这次改动的真实 diff。

改动意图：<为什么做、预期解决什么问题>
重点风险：<边界条件、异常处理、安全、并发或兼容性>

以代码为准。意图说明可能不完整甚至有误，请逐文件核实；
每个问题都给出文件、位置、触发条件和影响，不要只给风格建议。

四、把“意图”留在代码旁边

如果每次审查前都要手工整理上下文，很快就会嫌麻烦。更稳定的办法，是让写代码的代理在交接时把意图留下。

最实用的载体有三个：

  1. 结构化 commit message：适合本地 diff 和提交历史。
  2. PR 描述：适合 /review <PR> 和团队协作。
  3. 项目内 handoff 文件：适合跨会话、跨代理的复杂任务。

推荐的提交信息格式：

feat(auth): 增加登录失败次数限制

意图：连续失败 5 次后锁定账户 15 分钟，降低暴力破解风险。
改动：AuthService 增加失败计数与锁定判断，并补充相关测试。
风险点：并发登录下的计数竞态；锁定到期时间与时区处理。
取舍：计数暂存内存，服务重启后会清零。

这样的提交信息同时服务三类读者：

  • 未来的自己；
  • 团队里的真人审查者；
  • 接手审查的另一个模型。

CLAUDE.md 适合放长期项目规则。本地 /code-review 会遵守 CLAUDE.md，但不会读取 REVIEW.md；托管在 GitHub 上的 Claude Code Review 才会同时使用 CLAUDE.md 和审查专用的 REVIEW.md。

五、审查结果不是判决书

模型发现的问题仍然可能是误报。不要看到一条审查意见就立即修改，也不要看到“没有发现问题”就直接合并。

对每条重要发现，至少检查四件事：

  1. 位置是否准确：它引用的文件和代码是否真的存在？
  2. 触发条件是否成立：能否构造输入、状态或调用顺序复现？
  3. 影响是否真实：是生产 bug，还是纯风格偏好？
  4. 修复是否安全：修掉这里，会不会破坏另一个路径？

理想的闭环是：

生成代码
  → 审真实 diff
  → 验证发现
  → 修复
  → 跑测试和实际验证
  → 再看最终 diff

代码审查的目标不是“让模型多说几句话”，而是降低错误进入主分支的概率。

六、个人用户与团队用户怎么选

个人 Pro / Max

日常优先使用：

  • /code-review：提交前审当前改动；
  • /review <PR>：快速审查 PR；
  • /code-review ultra：重要改动合并前深审。

Team / Enterprise

除了本地命令，还可以启用托管的 Claude Code Review，让 GitHub PR 在创建、推送或手动触发时自动接受多代理审查。

这项托管服务目前是 research preview，单独通过 usage credits 计费，不占套餐内用量。它适合团队统一执行审查策略，但不是个人使用本地命令的前提。

关于 claude -p 的计费提醒

原定于 2026 年 6 月 15 日生效的“独立 Agent SDK 月度额度”后来已经暂停。按当前官方说明，Agent SDK、claude -p 和通过订阅认证的第三方应用，仍然从订阅使用额度中扣除；此前公布的独立月度 credit 暂未生效。

因此，不要基于旧公告估算自动化审查成本。高频、生产级自动化应重新核对当时的官方计费规则，或使用 Claude Platform API key 按量付费。

动手练习

找一个最近完成、但还没有合并的改动：

  1. 先运行 /diff，确认你知道本次改了什么。
  2. 运行 /code-review high，让它审当前真实 diff。
  3. 对最重要的一条发现，要求给出触发条件和证据。
  4. 自己复现或补一条测试，不要直接相信结论。
  5. 修复后重新运行相关测试，再看一次最终 diff。
  6. 如果改动已经开 PR，再用 /review <PR> 从 PR 视角通读一次。

练习的重点不是多运行一个命令，而是建立这条习惯：

实现者负责交付代码，审查者负责怀疑代码，验证负责决定谁是对的。
