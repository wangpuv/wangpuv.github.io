本课回答三个问题：CLAUDE.md 到底是什么、什么内容该写进去、为什么它必须精简（真正的原因不是省钱）。

适合：刚开始用 Claude Code、想让它在自己项目里更靠谱的人。

📌 基于 Claude Code 官方文档核对于 2026 年 6 月。产品更新较快，个别细节以官方文档与 /release-notes 为准。

一句话结论

CLAUDE.md 是 Claude 进你项目的「入职文档」，每次会话开头都会被完整载入。它的价值不在「写得全」，而在「高信号」——只放项目特有、工具兜不住、每次都需要、且 Claude 不说就会做错的红线。它靠累积变臃肿，所以要定期主动删；删什么的判断只能由你（项目主人）来下。

/init：起点，不是终点

  • /init 会扫描你的代码库，起草一份 CLAUDE.md（项目概览、构建/测试命令、目录结构、约定等）。注意它只是草稿，不是终稿。
  • 进阶：设环境变量 CLAUDE_CODE_NEW_INIT=1 再跑 /init，会进入交互式流程，连 skills、hooks、个人记忆一起带你过一遍，比默认版更完整。
  • 已有 CLAUDE.md 时，/init 会给改进建议，而不是覆盖。

心智模型：一份「活文档」

每个会话都从空白上下文开始 → CLAUDE.md 自动载入成为背景 → Claude 按这些规则干活 → 你发现它犯错、纠正一次（用 # 开头说一句，或 /memory 编辑）→ 写回文件 → 下一次会话自动带上这条规则。

关键：它不是一次写完的配置，而是越用越准的活文档。发现 Claude 重复踩坑，就把那条规则补进去。

什么该进 CLAUDE.md：四关测试

一行内容四关同时通过，才值得留：

  1. 项目特有（不是通用好习惯）
  2. 工具兜不住（没被 linter / CI / hook 强制）
  3. 每次会话都需要（不是只在某些场景才用）
  4. Claude 不被告知就会做错（它自己不会自然做对）

最锋利的一关是第 4 关：「Claude 不说就会反复踩的那个坑」。有些规则很重要，但 Claude 本来就会照做（如写清晰命名），那它也不必进去。

对照例子：

内容 判定
「遵循最佳实践、保持可读性」 ❌ 空泛，Claude 本就会
「用 4 空格缩进」（已配 Prettier） ❌ 工具已强制
「所有金额用整数分存储，绝不用浮点」 ✅ 项目特有 + 工具兜不住 + 会踩坑

没过四关的内容，该搬去哪（六个去处）

去处 适用 动作
✅ KEEP 四关全过的承重红线 留
📁 SCOPE 只在某些文件/场景才用（测试规范、API 规范），或多步流程 搬到 .claude/rules/X.md（带 paths: 作用域）或 skill，按需载入
🔧 ENFORCE 格式/命名/可静态检查的规则 改成 linter / CI / hook，删。「强制」胜过「提醒」
🔗 POINTER 复述了 docs 里已有的设计/schema 换成一行纯文字指针（「见 docs/X §Y」）
🗓️ STATUS 带日期的进度、评审、当前选型 搬到状态文档 / issue tracker / 自动记忆
❌ CUT 通用废话、文件内重复 删

「搬走」≠「删掉」：STATUS / SCOPE 的内容要落到具体新位置，别凭空消失。

两个隐蔽的反模式

不删内容，也会害你每轮背着大文档跑：

  1. @ 导入大文档：CLAUDE.md 里的 @path/to/file 是导入——启动时就把整份文件展开载入、每轮都在。所以 @ 一份 PRD/技术方案不省上下文，等于把它贴进来。→ 大文档一律用纯文字指针，@ 只留给小而每轮都需要的文件。
  2. 「每次开工先读 X / 总是先读这些文档」式命令：等于命令模型每轮把大文档拉进来，又膨胀又稀释注意力，还抵消了指针的好处。→ 改成按需、定向：「动到 X 时查 doc §Y」，只读相关段落。

为什么一定要精简？（真正的原因不是钱）

很多人以为是省 token。但有提示缓存：命中缓存时输入 token 大约只按基础价的十分之一计费，大文件其实不贵。所以「成本」这条理由站不太住。真正的三个原因是：

  1. 模型的注意力预算（最关键）：文件越长，重要规则越和噪音抢注意力，关键的几条被遵守得更差。缓存让你「存得便宜」，但对「用得好不好」毫无帮助。
  2. 上下文窗口空间：缓存便宜的是单价，不是容量。大文件每轮占着窗口，留给真正干活的空间更少、更早触发压缩。
  3. 缓存失效：CLAUDE.md 在前缀很靠前，你每改一次就打掉一次缓存——而「打磨 CLAUDE.md」这个动作本身就在反复打破「反正缓存了」的理想态。

升级后的心智模型：我们让它小，不是因为 token 贵，而是因为模型对高信号文件遵守得更好。 优化的是注意力，不是成本。

体量基准：官方建议每个 CLAUDE.md 控制在 200 行以内；高信号实践常更紧（约 80–120 行）。

为什么连最强的模型也会写出臃肿的 CLAUDE.md？

不是它不会写（它能把这些原则背出来），而是：

  • 你让它「写/更新文档」时，写作任务的默认拉力是详尽，不是「为注意力做减法」；多写在当下显得更负责。
  • 写文件的那一刻它满脑子都是你的项目，从信息很满的视角看，每一行都像承重的——它感受不到未来空白会话里的成本。
  • 文件是一轮轮「长」出来的：每次都在加，没有哪轮在删。臃肿几乎永远是累积问题。

所以「做减法」的判断必须由人在回路里补上。这不是模型失职，是这件事本身需要人来定目标。

相关机制速查

  • CLAUDE.md vs 自动记忆：两套互补、都每轮载入。CLAUDE.md 是你写的长期规则；自动记忆是 Claude 根据你的纠正自己记的（存于 ~/.claude/projects/<project>/memory/，MEMORY.md 前 200 行/25KB 载入，详情文件按需读）。长期稳定规则放前者；易变、临时的交给后者或 docs/。
  • 路径作用域规则：.claude/rules/X.md 文件头写 paths: ["tests/**"]，只在 Claude 接触匹配文件时才载入——把「只在部分场景用」的规则移出每轮预算。
  • Hook：要「不管 Claude 怎么决定都必须发生」的硬约束（如提交前必跑某命令），用 hook，而不是写进 CLAUDE.md（后者只是引导、不强制）。
  • HTML 注释：CLAUDE.md 里的 <!-- ... --> 注入上下文前会被剥掉——给人看的维护备注写这里，零 token 成本。
  • 命令即 skill：自定义命令现已并入 Skills；.claude/commands/x.md 和 .claude/skills/x/SKILL.md 都会生成 /x。Skill 按需载入，不占每轮预算。

常见疑问（FAQ）

Q：CLAUDE.md 常常是 Claude 自己写的，它不能自己保持精简吗？
A：「知道规则」≠「被要求按规则优化」。写文档的拉力指向详尽；且它在富上下文里、感受不到未来成本；臃肿是只加不删的累积病。做减法要靠你。

Q：团队有一大套编码规范（比如几十页 Java 规范），要写进去吗？
A：大部分不该。分流：格式/可静态检查的 → linter/CI/hook；完整规范文档 → 留 docs/ 用指针引用；只有少数非机械、项目特有、Claude 又老犯的设计约定才蒸馏成几条进去。

Q：有提示缓存，大文件不就便宜了吗，为什么还要限制大小？
A：钱这条确实不成立。但真正的约束是注意力（稀释）、上下文空间、和缓存失效（编辑即失效）。优化的是注意力，不是成本。

Q：「先读文档」和「@ 引用」不会每轮拉大文档、token 膨胀吗？
A：要分清三样：纯文字指针（惰性、便宜、不载入文档）/ @ 导入（饿汉、每轮全载）/ 「先读」命令（强制全读）。后两者是反模式，见上文。

动手练习

给你手头项目的 CLAUDE.md 做一次瘦身审计：

  1. 逐行过四关测试，给每行标上 KEEP / SCOPE / ENFORCE / POINTER / STATUS / CUT。
  2. 把 SCOPE 和 STATUS 的内容搬到具体新位置（.claude/rules/、docs/STATUS.md、issue），不要凭空删。
  3. 检查有没有 @ 导入大文档、有没有「每次先读 X」式指令，改成纯文字指针。
  4. 目标：砍到 120 行以内，红线一条不丢。

提示：这个流程本身可以做成一个 skill（如 /slim-claude-md），让 Claude 先出提案、你拍板、再动手。做的过程中发现的新坑，记得回灌进 skill——工具会越用越强。
