本课回答三个问题：权限规则和权限模式有什么区别、六种模式分别适合什么场景、怎样在减少弹窗的同时保住安全边界。

适合：已经开始让 Claude Code 修改项目，希望提高连续工作效率，又不想把推送、密钥和破坏性命令交给运气的人。

📌 基于 Claude Code 官方文档与本机 Claude Code 2.1.223 核对至 2026 年 8 月。权限系统变化较快，具体行为以当前版本的 /permissions、claude --help 和终端实测为准。

一句话心智模型

规则负责画出确定的边界，模式负责处理规则没有说到的动作。

可以先记住这个简化流程：

工具调用
  ↓
先查权限规则：deny → ask → allow
  ↓
没有命中
  ↓
再按当前权限模式处理

这就是本课最重要的区别：

  • permissions.allow / ask / deny 是长期、细粒度的规则；
  • default / acceptEdits / plan / auto / dontAsk / bypassPermissions 是会话的默认处置方式。

规则和模式不是二选一，而是叠加工作的。

一、系统 A：权限规则

权限规则通常写在 settings.json 的 permissions 字段里，也可以在 /permissions 中查看和管理。

它适合表达这些确定性要求：

  • 测试命令可以直接运行；
  • 推送代码必须让我确认；
  • 密钥文件不许读取；
  • 强制推送和破坏性命令直接禁止。

1. 三类规则与固定顺序

规则 命中后的结果
deny 直接阻止
ask 强制请求确认
allow 不弹权限确认，直接放行

评估顺序固定为：

deny → ask → allow

第一个命中结果生效，规则写得更具体，也不会改变这个顺序。

这带来两个重要结论：

  1. 宽泛的 allow 可以配合精确的 ask 或 deny，把少数高风险动作重新挖出来；
  2. 宽泛的 deny 不能再靠更精确的 allow 开一个例外，因为 deny 永远先判。

2. 裸工具名和带限定符不是一回事

"deny": ["Bash"]

裸工具名会匹配整个工具。作为 deny 使用时，Claude 甚至看不到这个工具。

"deny": ["Bash(rm -rf *)"]

带限定符只阻止匹配的调用。Bash 仍然可用，直到 Claude 尝试执行对应命令时才会被拦截。

3. 常用规则语法

Bash(npm run test *)
Read(/.env)
Edit(/src/**)
WebFetch(domain:docs.anthropic.com)
mcp__github__create_pull_request
Agent(code-reviewer)

这里有几个容易踩坑的点。

Bash 的 * 可以跨越多个参数

Bash(git *)

会匹配 git log --oneline --all，因为一个 * 可以匹配包含空格在内的任意字符序列。

空格决定是否要求单词边界

Bash(ls *)

匹配 ls -la，但不匹配 lsof。

Bash(ls*)

两者都会匹配。

复合命令会拆开检查

git status && npm test

Claude Code 会分别检查 git status 和 npm test。只允许前半段，不代表整条复合命令都能运行。

路径规则使用 Read 和 Edit

当前版本会用 Read(path) 检查读取，用 Edit(path) 统一检查内置文件编辑工具。

在项目级 .claude/settings.json 中：

Read(/.env)
Edit(/src/**/*.ts)

这里的单斜杠 / 表示“相对于这份设置文件所属的项目根目录”，不是文件系统根目录。真正的绝对路径需要以 // 开头。

另外，Read 的 deny 会连同该路径的内置编辑一起阻止；如果某个目录无论如何都不能被修改，再补一条 Edit deny 会更清楚。

4. Bash 规则不是操作系统沙箱

Read 和 Edit 规则只约束 Claude Code 的内置文件工具。它们不能阻止 Bash 里的 cat .env，也不能阻止 Python、Node 或自定义二进制自己打开文件。

如果你需要进程级的硬隔离，要启用 sandbox。 启用后，Read / Edit 的路径限制可以合并进操作系统级的文件系统边界；没有 sandbox 时，不要把这些规则当成对子进程的强制隔离。

同样，不要尝试只用 Bash 字符串模式精确限制 curl 的 URL。参数顺序、变量、重定向和短链接都会让这种规则变脆。更稳的做法是：

  • 禁止 Bash 网络工具；
  • 给 WebFetch(domain:...) 配置明确域名；
  • 或用 PreToolUse hook 做真正的参数校验。

二、规则来自哪里：作用域与优先级

从高到低，常见设置来源是：

  1. 企业托管设置；
  2. 命令行参数和 --settings；
  3. .claude/settings.local.json；
  4. .claude/settings.json；
  5. ~/.claude/settings.json。

数组型配置会合并并去重，而不是简单用高优先级数组覆盖低优先级数组。

因此：

  • 用户级 allow 与项目级 allow 可以同时存在；
  • 任意作用域里的 deny 都能压住其他作用域里的 allow；
  • 项目级共享设置中的 allow 只有在你信任该工作区后才会生效。

选择作用域的实用原则

放在哪里 适合什么
~/.claude/settings.json 个人跨项目偏好
.claude/settings.json 团队共同边界，可进 Git
.claude/settings.local.json 只属于自己的项目例外，不提交
托管设置 组织强制策略，开发者不能覆盖

defaultMode: "auto" 是一个特殊例外：为了防止仓库让自己自动获得更宽松的模式，当前版本会忽略项目和本地设置中的这个值。要把 Auto 设为默认，只能放在用户级或托管设置中。

三、内置只读命令：无需确认，但不是无视规则

Claude Code 内置了一组只读 Bash 命令，通常在各种模式下都不需要权限弹窗，例如：

ls  cat  echo  pwd  head  tail  grep  find
wc  which  diff  stat  du  cd

以及 git status、git diff、git log 等只读 Git 形式。

但这里不能误解成“它们无视权限规则”。你仍然可以为某个只读命令写 ask 或 deny。

一些带写入能力、执行能力、网络路径、危险 glob，或 Claude Code 无法完整解析的形式，也会重新进入权限判断。

四、系统 B：六种权限模式

权限模式决定规则没有明确覆盖时，Claude Code 默认怎样处理工具调用。

界面名称 配置值 默认行为 适合场景
Manual default 读取自动，编辑和多数命令询问 敏感项目、刚开始使用
Accept edits acceptEdits 自动编辑项目文件和常见文件系统命令 日常迭代开发
Plan plan 研究、探索、提出方案，不直接改源码 大改动前先理清方案
Auto auto 通过后台分类器审查需要判断的动作 方向可信的长任务
Don't ask dontAsk 未预先批准的动作直接拒绝，不弹窗 CI、无人交互脚本
Bypass permissions bypassPermissions 大多数动作立即执行，跳过常规安全检查 隔离容器或一次性 VM

从 Claude Code 2.1.200 开始，界面把 default 显示为 Manual，命令行也接受 manual 作为别名。配置文件和集成中仍常见 default。

Shift+Tab 默认怎样循环

终端中按 Shift+Tab，基础循环是：

Manual → Accept edits → Plan

Auto 在账户、模型和组织策略满足条件时加入循环；Bypass 只有在启动时明确启用后才会出现；dontAsk 从不出现在循环里，需要通过参数或设置启用。

当前版本也可以在启动时直接指定：

claude --permission-mode plan
claude --permission-mode auto
claude --permission-mode dontAsk

五、Accept edits、Auto 和 Bypass 到底差在哪

这是本课最容易混淆、也最值得记住的部分。

acceptEdits auto bypassPermissions
核心机制 按动作类别放行 独立分类器逐动作判断 跳过常规权限与安全检查
项目内文件编辑 自动 自动 自动
一般 Shell 与网络动作 继续按规则询问 交给分类器 通常直接执行
是否有风险判断模型 没有 有 没有
推荐环境 人在场的日常开发 方向明确的长任务 只有隔离容器或 VM

Accept edits 不等于全自动

它会自动放行项目范围内的文件编辑，以及 mkdir、touch、rm、rmdir、mv、cp、sed 等常见文件系统命令。

但测试、推送、联网、装包等其他命令仍按权限规则处理。进入这个模式前先提交一次 Git，会让回滚更轻松。

Auto 不等于 YOLO

Auto 没有取消安全判断，而是把原本由人完成的部分审批交给独立分类器。

它适合：

  • 目标清楚、影响范围可控的长任务；
  • 需要运行测试、修改文件、反复修复的连续工作；
  • 希望减少弹窗，但仍需要安全兜底的场景。

它不适合：

  • 生产部署、密钥操作、共享基础设施；
  • 你还没想清楚目标和边界的任务；
  • 无法接受分类器误判或漏判的高风险操作。

Bypass 只适合隔离环境

Bypass 会跳过常规权限提示和安全检查，保护路径也可能直接写入。

Bypass 会跳过常规权限层，因此不要指望普通 ask / deny 继续充当可靠边界。当前版本只明确保留删除文件系统根目录或用户主目录时的熔断提示；管理员也可以在会话启动前禁用这个模式。

这些都不等于完整保护。在日常开发机上，不要把 Bypass 当成省弹窗的快捷方式。

六、Auto 模式怎样做决定

日常可以把 Auto 的判定过程理解为四步：

  1. 先处理 deny、ask、allow 规则；
  2. 工作目录内的只读动作和普通文件编辑通常直接通过，保护路径除外；
  3. 其他动作交给分类器；
  4. 分类器阻止后，Claude 会收到阻止结果并尝试更安全的替代方案。

有几个重要例外：

  • 显式 ask 始终保留人工检查点；
  • 写保护路径时，即使命中 allow，Auto 仍可能交给分类器；
  • 进入 Auto 时，Bash(*)、通配解释器、包管理器运行命令、Agent 等过宽的 allow 规则会暂时被移除；
  • 离开 Auto 后，这些被暂时移除的规则会恢复。

分类器看什么

分类器会看到：

  • 用户消息；
  • 待执行的工具调用；
  • CLAUDE.md 中的项目上下文。

它不会直接看到工具执行结果。这样可以减少文件或网页中的恶意指令直接影响审批判断。

与此同时，服务端还有一层探针扫描进入上下文的工具结果，发现可疑内容时先做提示。

分类器不是你的会话模型

分类器不跟随 /model。官方当前更稳定的表述是：它使用服务端配置的独立模型，具体模型可能随服务端配置变化。

真正需要记住的是：它是一条独立的安全判断路径，不是主模型自己给自己批准。

成本与延迟

分类器调用会计入 token 使用，并在需要检查的动作前增加一次往返延迟。

读取和工作目录内的普通编辑通常会跳过分类器，所以主要开销来自 Shell、网络和外部系统操作。

真正容易放大成本的，往往不是单次分类，而是 Auto 让 Claude 连续运行、反复测试和修复。长任务仍要定期查看 /usage 和实际进展。

多次阻止后的兜底

如果分类器连续阻止 3 次，或一个会话累计阻止 20 次，Auto 会暂停并恢复人工提示。批准后才继续 Auto。

这些阈值当前不可配置。

七、口头边界会被压缩，硬边界必须写进规则

在 Auto 中，你说：

先不要 push，等我确认。

分类器会把这句话当成阻止信号。

但它会从当前转录中重新读取这个边界。如果 /compact 把这条消息压缩掉，口头边界可能随之消失。

所以：

  • 临时偏好可以在对话里说；
  • 必须保证的边界要写入 permissions.ask 或 permissions.deny；
  • 生产系统、强推、密钥和不可逆操作，不要只靠聊天记录约束。

八、Plan 模式也有一个新变化

过去可以简单地说：Plan 只读、只探查、不执行其他命令。

当前版本更准确的说法是：

  • Plan 仍然不会直接编辑你的源码；
  • 内置只读命令可以运行；
  • 当 Auto 可用且 useAutoModeDuringPlan 保持默认开启时，一些探索性 Shell 命令会交给分类器判断，而不是一律弹窗。

因此，Plan 的核心承诺是“先研究并产出方案，不直接开始改代码”，而不是“绝对不会运行任何非只读命令”。

九、一个 FastAPI 项目的起步配置

把下面示例放进项目的 .claude/settings.json：

{
  "permissions": {
    "allow": [
      "Bash(pytest *)",
      "Bash(python -m pytest *)",
      "Bash(uv run pytest *)",
      "Bash(ruff check *)",
      "Bash(ruff format --check *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(pip install *)",
      "Bash(uv add *)",
      "Bash(alembic upgrade *)"
    ],
    "deny": [
      "Read(/.env)",
      "Read(/.env.*)",
      "Edit(/.env)",
      "Edit(/.env.*)",
      "Bash(git reset --hard *)",
      "Bash(git push --force *)",
      "Bash(rm *)"
    ],
    "defaultMode": "default"
  }
}

它的设计逻辑是：

  • allow：高频、可重复、影响范围小的验证动作；
  • ask：经常需要，但可能影响环境或远端状态的动作；
  • deny：密钥、明确写出的强推与硬重置形式，以及所有 rm 命令；
  • defaultMode：项目默认保持 Manual，需要时在会话中临时切到 Accept edits 或 Auto。

这个配置只是起点，不是万能安全模板。

Bash 模式无法覆盖所有同义写法，文件规则也不能替代进程级 sandbox。真正重要的项目应该把权限规则、sandbox、分支保护、CI 审核和最小权限凭据一起使用。

十、Auto 的配置入口

如果 Auto 经常把公司内部仓库、域名或云资源当成陌生基础设施，可以通过 autoMode 配置补充上下文。

先注意配置位置：分类器不会读取团队共享的 .claude/settings.json。个人跨项目配置放在 ~/.claude/settings.json，个人的项目专属配置放在 .claude/settings.local.json；企业还可以使用托管设置，自动化场景也可以通过 --settings 或 Agent SDK 传入。

常见入口包括：

  • autoMode.environment：声明可信仓库、域名、存储桶和基础设施；
  • autoMode.hard_deny：无条件阻止，用户意图和 allow 都不能覆盖；
  • autoMode.soft_deny：阻止高风险动作，但明确的用户意图或 allow 例外可以覆盖；
  • autoMode.allow：为 soft_deny 增加例外；
  • autoMode.classifyAllShell：让更多 Shell 命令都经过分类器。

这里有一个非常重要的规则：只要显式设置 environment、allow、soft_deny 或 hard_deny，却没有在数组中加入 "$defaults"，就会替换该字段的整套内置规则，而不是在默认规则后面追加。

例如，希望保留内置规则再增加一条时，应写成：

{
  "autoMode": {
    "soft_deny": [
      "$defaults",
      "不要修改生产环境的 Terraform 配置"
    ]
  }
}

如果省略 "$defaults"，这一字段原有的内置规则会全部被丢弃。除非你准备完整接管规则列表，否则不要省略它。

查看当前有效配置：

claude auto-mode config

查看内置默认规则：

claude auto-mode defaults

让 Claude 检查自定义规则是否模糊、重复或容易误判：

claude auto-mode critique

这类配置本身也是安全边界。不要为了消除一次误报，就写一个覆盖范围过大的例外。

十一、怎样选择模式

如果你拿不准，可以直接按这个顺序判断：

只是想先看懂项目

用 plan。

人在电脑前，主要嫌文件编辑弹窗多

用 acceptEdits。

是一个方向明确、需要连续测试修复的长任务

先写好 ask / deny，再考虑 auto。

是 CI 或无人交互脚本，只允许固定命令

用 dontAsk，提前列出 allow。

是一次性、可丢弃、与宿主机隔离的环境

才考虑 bypassPermissions。

想让某一条命令不再询问

加精确的 allow 规则，不要为了一个命令把整个会话切到更宽松的模式。

十二、避坑清单

  • [ ] 不要把 Accept edits 当成全自动，它只自动放行文件编辑和一组常见文件系统动作。
  • [ ] 规则顺序是 deny → ask → allow，具体规则不会推翻更早命中的宽泛规则。
  • [ ] 裸工具名会匹配整个工具；带限定符只约束一类调用。
  • [ ] Bash(ls *) 和 Bash(ls*) 的边界不同。
  • [ ] 复合 Shell 命令会拆成多个子命令逐一检查。
  • [ ] 内置只读命令默认免提示，但仍可被显式 ask 或 deny 约束。
  • [ ] Read / Edit 规则不是任意子进程的操作系统沙箱。
  • [ ] 项目设置不能让自己默认进入 Auto；defaultMode: "auto" 应放在用户或托管设置。
  • [ ] autoMode 不读取共享的 .claude/settings.json，个人项目配置应放在 .claude/settings.local.json。
  • [ ] 自定义 Auto 规则时用 "$defaults" 继承内置规则，避免无意间整组替换。
  • [ ] Auto 是研究预览，会降低弹窗，但不保证绝对安全。
  • [ ] Auto 下过宽的 allow 会被暂时移除，精确规则才更可靠。
  • [ ] 口头边界可能被 /compact 清掉，硬要求要写成规则。
  • [ ] Bypass 只用于隔离容器或一次性 VM，不用于日常开发机。
  • [ ] 先用 /permissions 看清规则来源，再处理“为什么它还在问”或“为什么它没问”。

本课小结

安全又高效的 Claude Code 工作流，不是永远停在 Manual，也不是直接打开 Bypass。

更合理的方式是：

  1. 用 deny 写下绝不能越过的底线；
  2. 用 ask 保留少数人工检查点；
  3. 用精确的 allow 消除高频、安全动作的弹窗；
  4. 再根据任务选择 Manual、Accept edits、Plan、Auto 或 Don't ask；
  5. 只有隔离环境才考虑 Bypass。

先把规则写清楚，再选择模式。自动化才能越走越快，而不是越走越险。
